# Календарь звонков (продолжение)

[![hexlet-check](https://github.com/znaeff/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/znaeff/ai-for-developers-project-387/actions)

Учебное приложение от Hexlet для бронирования встреч.

**Публичная версия:** [https://calendar-booking-lyk4.onrender.com](https://calendar-booking-lyk4.onrender.com)

## Роли

- Владелец — администратор календаря, его функции доступны без регистарции по заранее определённому URL-у, он создаёт типы встреч с описанием и длительностью, может смотреть встречи, соданные гостями.
- Гость — пользователь календаря, его функции доступны без регистарции, он бронирует (регистрирует, создаёт) встречи с типом, созданным администратором в свободные слоты времени.


## Сценарий работы для создания встречи
- Владелец видит список типов встреч.
- Владелец при отстуствии нужного типа создаёт его с описанием и длительностью.
- Гость видит список типов встреч.
- Гость выбирает нужный тип встречи.
- Гость видит календарь со свободными слотами на следующие 14 дней, считая от текущего времени.
- Гость выбирает нужный слот и бронирует встречу выбранного типа со своими именем и почтой.
- Слоты, которые заняла встреча, больше не доступны для бронирования.

## Расписание и слоты

Владелец работает по будням, с понедельника по пятницу, с 09:00 до 18:00 по поясу `Europe/Moscow` (UTC+03:00, без перехода на летнее время). Выходные исключены.

- Кандидаты на начало слота идут каждые 15 минут, начиная с 09:00.
- Длительность должна быть кратной 15 минутам и выбирается из фиксированного списка: 15, 30, 45 или 60 минут.
- Встреча должна целиком помещаться до 18:00: подходят только старты, для которых `start + durationMinutes <= 18:00`.
- Для 45-минутной встречи кандидаты начинаются в 09:00, 09:15, 09:30, 09:45 и так далее.
- Показываются только будущие слоты (`start > сейчас`) в окне до 14 дней (`start < сейчас + 14 дней`).
- Занятые Брони не скрывают Слоты из выдачи: если встреча 09:00–09:45 уже забронирована, Слоты 09:00, 09:15 и 09:30 остаются в списке с `isAvailable: false` и показываются серыми, а следующий свободный старт — 09:45. У Владельца один календарь, поэтому Брони **всех** Типов встреч делают недоступными пересекающиеся Слоты: Бронь Типа A блокирует пересекающиеся Слоты Типа B. Подробнее — в `docs/adr/0004-slot-rules.md`.

## Стек

- **Монорепозиторий:** pnpm workspaces (`apps/backend`, `apps/frontend`), версии инструментов управляются через [mise](https://mise.jdx.dev/) (Node.js 22 и pnpm указаны в `mise.toml`).
- **Бэкенд:** TypeScript + Node.js 22, встроенный модуль `node:http`. API: `GET/POST /meeting-types`, `GET /meeting-types/:id/slots`, `GET/POST /bookings`; служебный `GET /reserve` возвращает текст `Reserved`. В контейнере сервер также раздаёт собранный фронтенд и понимает префикс `/api`. Контракт описан в `docs/adr/0003-api-contract.md`.
- **Фронтенд:** TypeScript, Vite, React, shadcn/ui на базе Tailwind CSS v4. Стартовая страница со ссылками на страницы гостя и владельца, навигация без роутера. На `/owner` Владелец создаёт Типы встреч, видит их список и список предстоящих Броней с кнопкой «Обновить»; список Броней также обновляется при возврате фокуса на вкладку. На `/guest` Гость выбирает Тип встречи, видит Слоты, сгруппированные по дням, затем выбирает свободный Слот, вводит имя и почту и получает подтверждение Брони.
- **Docker:** multi-stage образ на Node 22; один контейнер отдаёт интерфейс и API на одном порту (`PORT`, по умолчанию `3000`).
- **Контракт:** TypeSpec (`contracts/main.tsp`) → OpenAPI (`contracts/openapi/openapi.json`) → TypeScript SDK (`apps/frontend/src/api/generated`).
- **Тесты:** ESLint (линтер), `tsc --noEmit` (проверка типов), Vitest (HTTP- и contract-тесты бэкенда), Playwright (end-to-end тесты фронтенда). Все проверки, включая генерацию, e2e и Docker, объединяет `mise run check`.

## Контракт и SDK

Источник истины для API — `contracts/main.tsp`. Из него одной командой генерируются OpenAPI и клиентский SDK:

```bash
mise run generate
```

- `contracts/openapi/openapi.json` — OpenAPI 3.0.
- `apps/frontend/src/api/generated/**` — TypeScript SDK, который использует фронтенд.

Сгенерированные файлы коммитятся и не редактируются вручную. Меняйте `contracts/main.tsp` и повторяйте генерацию. Серверный код не генерируется: бэкенд работает на `node:http`, поэтому обработчики поддерживаются вручную и проверяются contract- и HTTP-тестами.

## Docker

Образ содержит собранные бэкенд и фронтенд; для запуска контейнера не нужны локальные Node.js и pnpm.

```bash
mise run docker:build   # собрать образ calendar-booking:local
mise run docker:smoke   # поднять контейнер и проверить страницы и API
mise run docker:run     # запустить контейнер на http://localhost:3000
```

Порт внутри контейнера задаётся переменной `PORT`. Например, на 8080:

```bash
docker run --rm -e PORT=8080 -p 8080:8080 calendar-booking:local
```

Docker build и контейнерный smoke входят в `mise run check`; отдельного Docker workflow больше нет.

## Render

Приложение развёрнуто как публичный Web Service `calendar-booking` в регионе Frankfurt на free-плане. Сервис подключён к репозиторию `znaeff/ai-for-developers-project-387`, ветке `main`, и собирает образ из корневого `Dockerfile` (`dockerContext: .`). Render сам задаёт переменную окружения `PORT`; приложение слушает именно этот порт. Auto-deploy включён и срабатывает на новые коммиты в `main`. Free-план может засыпать после периода неактивности — первый запрос после простоя может занять несколько секунд.

Ранее сервис был подключён к `znaeff/ai-for-developers-project-386`; теперь этот репозиторий не является источником деплоя.

### Подключение Render MCP без секретов

`opencode.json` уже содержит конфигурацию удалённого MCP-сервера:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "render": {
        "type": "remote",
        "url": "https://mcp.render.com/mcp",
        "oauth": false,
        "headers": {
          "Authorization": "Bearer {env:RENDER_API_KEY}"
        }
      }
    }
  }
}
```

Ключ хранится только в переменной окружения `RENDER_API_KEY`, в файлах репозитория его нет.

1. Создайте API key в [Render Dashboard](https://dashboard.render.com/u/settings#api-keys).
2. Экспортируйте его в окружении, из которого запускается OpenCode:
   ```bash
   export RENDER_API_KEY='ваш-ключ'
   ```
3. Если фоновый сервис OpenCode уже запущен, перезапустите его, чтобы он увидел новую переменную:
   ```bash
   opencode service restart
   ```
4. Проверьте подключение:
   ```bash
   opencode mcp list
   ```
   В выводе должно быть `render connected`.
5. Убедитесь, что выбран нужный workspace: вызовите `list_workspaces` через MCP и уточните workspaceId, если workspace один.
6. Не коммитьте ключ: `.env*` игнорируется git и Docker build context, в репозитории остаётся только `.env.example` с именем переменной. OpenCode не загружает `.env` автоматически — переменная должна быть реально экспортирована в окружении процесса.

## Тесты

```bash
mise run check
```

Одна команда последовательно запускает:

1. генерацию OpenAPI и SDK с проверкой отсутствия diff;
2. линтер (`pnpm lint`);
3. проверку типов (`pnpm typecheck`);
4. HTTP- и contract-тесты бэкенда (`pnpm test`);
5. end-to-end тесты Playwright с реальными бэкендом и Vite (`pnpm test:e2e`);
6. сборку Docker-образа (`pnpm docker:build`);
7. контейнерный smoke (`pnpm docker:smoke`).

Эти же проверки выполняются в GitHub Actions на каждый пуш и pull request (workflow `.github/workflows/ci.yml`). HTTP-тесты сами поднимают бэкенд на свободном порту, создают Типы встреч и Брони через API и закрывают сервер; запускать бэкенд отдельно не нужно.

Для точечного запуска e2e:

```bash
mise run test:e2e
```

Playwright сам поднимает бэкенд на 3000 (с `E2E_RESET=1`) и Vite на 5173 и проверяет реальные страницы; перед каждым тестом fixture вызывает `POST /api/__test__/reset`, очищая Типы встреч и Брони. Тесты выполняются последовательно (`workers: 1`), чтобы сброс не пересекался с параллельными сценариями. Для быстрой проверки без генерации, e2e и Docker используйте `mise run check:fast`.

## OpenCode GitHub agent

В репозитории настроен официальный GitHub App `opencode-agent`; альтернативный агент с теми же сценариями не используется, поэтому отдельного сравнения в этом README нет.

Workflow `.github/workflows/opencode.yml` запускается на события `issue_comment` и `pull_request_review_comment` типа `created`. Команда должна быть в начале комментария; обрабатываются `/oc` и `/opencode` (явно задано через `mentions`). Запуск разрешён только владельцу репозитория (`author_association == 'OWNER'`); для этого персонального репозитория это майнтейнер. Комментарии ботов и недоверенных fork игнорируются.

Права job ограничены: `contents: read`, `id-token: write` и `issues: write`; checkout выполняется с `persist-credentials: false`. Авторизация action — через OIDC GitHub App `opencode-agent`. Внутри сессии `gh` получает короткоживущий `GH_TOKEN` из автоматического `GITHUB_TOKEN` с правом `issues: write` — это не новый секрет; он нужен скиллам вроде `to-spec`, чтобы публиковать issue. Ключ модели лежит в GitHub Secrets как `OPENCODE_API_KEY`, его значение в репозитории не хранится и не выводится.

Используется модель `opencode/big-pickle` через OpenCode Console. Назначение воркфлоу — отвечать на команды в issue и pull request: объяснять код, документацию и Issue, а при задачах на изменения — готовить правки. Результат публикуется комментарием в соответствующем треде; прогон виден во вкладке Actions (`workflow: opencode`).

Явно принятое решение по `share`: `share: "false"`. Сессии агента автоматически не публикуются; ссылки на каждый прогон и ответ добавляются в issue/PR вручную.

На свежем раннере доступны скиллы из `.agents/skills/` и настройки из `docs/agents/` — они лежат в репозитории и попадают в checkout.

### Автотриаж новых обращений

Workflow `.github/workflows/auto-triage.yml` запускается только на событие `issues: [opened]` и делает первичный триаж по скиллу `triage`. Закреплённый action `anomalyco/opencode/github` умеет работать только с событиями `issue_comment` и `pull_request_review_comment`, поэтому здесь используется CLI `opencode run` с зафиксированной версией `2.3.2`; установщик скачивается во временную директорию и проверяется по SHA-256 перед запуском. Модель та же — `opencode/big-pickle`, ключ по-прежнему лежит в Secrets как `OPENCODE_API_KEY` и не выводится в логи.

Джоб запускается только если автор issue — владелец репозитория, это не бот, событие не относится к pull request и у issue нет ни одной из пяти state-меток (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). Благодаря этому готовые тикеты и спеки, которые создаёт агент с меткой `ready-for-agent`, автотриаж пропускает: run может появиться в списке, но джоб в нём будет `skipped`, без вызовов модели. Материал из тела issue считается данными, а не инструкциями.

Job имеет минимальные права: `contents: read` для checkout скиллов и документации и `issues: write` для меток и комментария. OIDC здесь не используется, поэтому `id-token: write` не выдаётся; `gh` внутри сессии получает короткоживущий `GH_TOKEN` из автоматического `GITHUB_TOKEN`. Ограничения: `timeout-minutes: 15`, concurrency на номер issue без отмены уже идущего прогона, `persist-credentials: false`.

Агент применяет только начальное состояние: одну категорию (`bug` или `enhancement`) и `needs-triage`, затем публикует один комментарий с обязательным дисклеймером скилла и рекомендацией следующего состояния. Комментарии триажа пишутся по-русски; канонические метки (`bug`, `enhancement`, `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), пути, команды и идентификаторы кода остаются без перевода. Он не меняет код, не создаёт коммиты, ветки и pull request, не закрывает issue и не ставит `needs-info`, `ready-for-agent`, `ready-for-human` или `wontfix` без решения мейнтейнера. Прогон виден во вкладке Actions (`workflow: auto-triage`, имя `auto-triage issue #<n>`), результат — метки и комментарий в самом issue.

### Авторевью pull request

Workflow `.github/workflows/opencode-review.yml` публикует независимое ревью PR. Он запускается на `pull_request` с типами `opened`, `synchronize`, `reopened`, `ready_for_review` и `edited`; событие `edited` учитывается только при изменении тела PR. Ревью не заменяет решение человека: публикуется только `COMMENT`, без `APPROVE` и `REQUEST_CHANGES`, а merge остаётся ручным.

Проходят только нечерновиковые PR этого же репозитория от `OWNER`, `MEMBER`, `COLLABORATOR` или `opencode-agent[bot]`. PR из fork, черновики и остальные боты уходят в ручное ревью. Права job: `contents: read`, `pull-requests: write`, `issues: write`, `actions: read`, `checks: read`, `statuses: read`; `id-token` не выдаётся. Таймауты: 75 минут у job, 60 у шага модели и 10 у публикации. `concurrency` по номеру PR с `cancel-in-progress: true` отменяет устаревшее ревью при новом push.

Checkout выполняется по точному `head.sha`, а не по merge-ref. Модель работает в отдельном каталоге `$RUNNER_TEMP/review` с `OPENCODE_DISABLE_PROJECT_CONFIG=true`; туда попадают `.review/` и снимок исходников, но не `REVIEW.md`, `AGENTS.md`, `.agents/`, `opencode.json` и другие файлы инструкций/конфигурации из PR. Критерии `REVIEW.md` и `AGENTS.md` читаются из базовой ветки; их доступность записывается в `.review/criteria-status.txt`, а отсутствующий файл помечается `unavailable` и не считается проверенным. Так PR не может ослабить правила своего ревью.

Ревьюер получает diff, изменённые файлы, связанные issues, прошлые ревью и статус обязательной проверки `check` для head SHA. Ожидание CI ограничено 30 минутами; если `check` не завершился, фиксируется `CI pending`, а не вывод о падении. Публикуются общий комментарий и inline-замечания; замечание без подходящей строки остаётся в общем комментарии. На PR действует лимит 5 попыток, попытка резервируется скрытым маркером до вызова модели. Статусы видны в комментариях: `reviewed@<sha>`, `limit-reached` и `error`; отсутствие отчёта не означает отсутствие замечаний.

Шаблон `.github/pull_request_template.md` требует указать проверки с кодом выхода и SHA, риск `R0–R3`, способ отката, разбор замечаний и человеческое решение о merge. Полные критерии и формат замечаний — в `REVIEW.md`.

### Release Please

Workflow `.github/workflows/release-please.yml` запускается на push в `main` и вручную через `workflow_dispatch`. Он создаёт release PR из Conventional Commits и обновляет `CHANGELOG.md`, `package.json` и `.release-please-manifest.json`.

Репозиторий не разрешает `GITHUB_TOKEN` создавать pull request, поэтому action получает fine-grained PAT из секрета `RELEASE_PLEASE_TOKEN`. PAT должен иметь доступ только к этому репозиторию и права `Contents: Read and write`, `Issues: Read and write`, `Pull requests: Read and write`; `Metadata: Read` выдаётся автоматически. Значение секрета в репозитории не хранится и не выводится в логи. При истечении или отзыве PAT release-please перестанет создавать PR, поэтому токен нужно ротировать заранее.

Включать настройку `Allow GitHub Actions to create and approve pull requests` не требуется. Для ручной проверки после изменения workflow используйте `gh workflow run release-please.yml --repo znaeff/ai-for-developers-project-387 --ref main`; release PR проходит обычный CI и мержится человеком.

### Браузерные доказательства PR

Job `head-browser-evidence` в `.github/workflows/ci.yml` запускается только на `pull_request`, работает без секретов и модели и проверяет два согласованных сценария:

- `@head-browser-main` — Гость бронирует свободный Слот и видит подтверждение; Слот становится недоступным;
- `@head-browser-adjacent` — Владелец открывает `/owner` и видит новую Бронь.

Checkout выполняется по точному `head.sha` PR, а шаг проверки сравнивает `git rev-parse HEAD` с этим SHA и падает при расхождении. Результат складывается в артефакт `head-browser-<sha>`: `head-sha.txt`, `results.json`, `summary.txt` и Playwright traces в `traces/`. Артефакт загружается даже при падении тестов, чтобы был виден фактический результат.

После нового push появляется новый артефакт для нового SHA. Перед merge человек обязан сверить SHA в артефакте с текущим head SHA PR; старый артефакт доказательством не является. Требования к сценариям и артефакту зафиксированы в `REVIEW.md` и `.github/pull_request_template.md`.

## Использование

```bash
mise run dev:backend    # бэкенд: http://localhost:3000/meeting-types
mise run dev:frontend   # фронтенд: http://localhost:5173
```

Можно запустить оба процесса одной командой: `mise run dev`. Откройте http://localhost:5173 — на стартовой странице «Календарь звонков» две ссылки: «Бронировать встречу» (`/guest`) и «Управление календарём» (`/owner`). На странице владельца доступна форма создания Типа встречи, список уже созданных Типов встреч и список предстоящих Броней с датой и временем по Москве, именем и почтой Гостя; кнопка «Обновить» перезагружает список Броней, а при возврате фокуса на вкладку он обновляется автоматически. На странице гостя Гость видит список Типов встреч, выбирает нужный, получает свободные Слоты по дням, выбирает Слот, вводит имя и почту и получает подтверждение Брони; занятый Слот остаётся в списке серым и недоступным, а при конфликте `409` выбранный Слот сбрасывается, список Слотов перезагружается и гость видит сообщение «Этот слот уже занят. Пожалуйста, выберите другое время.». Вернуться к списку Типов встреч можно кнопкой «Выбрать другой тип». С обеих страниц можно вернуться «На главную».

## API

Типы встреч и Брони хранятся в памяти процесса и сбрасываются при его рестарте. Машинный контракт — `contracts/openapi/openapi.json`, его источник — `contracts/main.tsp`; rationale записан в `docs/adr/0003-api-contract.md`.

- `GET /meeting-types` — список Типов встреч.
- `POST /meeting-types` — создание Типа встречи. Тело запроса: `{ "title": "…", "description": "…", "durationMinutes": 30 }`. `durationMinutes` — одно из значений `15`, `30`, `45`, `60`. Успех — `201` с созданным Типом встречи; невалидные данные, битый JSON или тело больше 1 МиБ — `400`; Тип с такой длительностью уже существует — `409` с телом `{ "error": "…" }`.
- `GET /meeting-types/:id/slots` — Слоты выбранного Типа встречи на ближайшие 14 дней. Ответ — массив `{ "startsAt": "2026-01-05T09:00:00+03:00", "endsAt": "2026-01-05T09:30:00+03:00", "isAvailable": true }`; даты в ISO 8601 с московским смещением `+03:00`. Слоты, пересекающиеся с Бронями **любых** Типов встреч, возвращаются с `isAvailable: false`; гость видит их серыми и не может выбрать. Для неизвестного `id` — `404` с телом `{ "error": "…" }`.
- `GET /bookings` — список Броней, отсортированный по времени начала (`startsAt`). С `?upcoming=true` возвращаются только Брони с `startsAt >= сейчас`; именно этот режим использует страница владельца. Ответ — массив Броней без вычисляемых полей: `{ "id": "…", "meetingTypeId": "…", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com", "createdAt": "2026-01-05T05:12:34.000Z" }`. Поля `meetingTypeTitle` в ответе нет: название Типа встречи клиент находит по `meetingTypeId`. Если Броней нет, возвращается `[]`.
- `POST /bookings` — создание Брони. Тело запроса: `{ "meetingTypeId": "…", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com" }`. `meetingTypeId` и `startsAt` обязательны, `startsAt` должен совпадать с одним из свободных Слотов выбранного Типа. Успех — `201` с Бронью `{ "id": "…", "meetingTypeId": "…", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com", "createdAt": "2026-01-05T05:12:34.000Z" }`. Ошибки возвращаются с телом `{ "error": "…" }`: `400` — пустое имя, некорректная почта, отсутствующие или некорректные `meetingTypeId`/`startsAt` (включая время вне доступных Слотов), битый или слишком большой JSON; `404` — неизвестный Тип встречи; `409` — Слот пересекается с существующей Бронью любого Типа встречи. Проверка занятости и запись Брони выполняются атомарно в рамках одного процесса.

Для e2e-тестов при `E2E_RESET=1` доступен служебный `POST /__test__/reset` (в dev через Vite — `/api/__test__/reset`): он очищает Типы встреч и Брони и возвращает `204`. Без этой переменной эндпоинт отвечает `404`.

В dev-режиме Vite проксирует `/api/*` на бэкенд и снимает префикс `/api`; в production тот же префикс обрабатывает `createServer()`.

Бэкенд по-прежнему отвечает на `GET /reserve` текстом `Reserved`; кнопка `Check` с главной убрана. Запрос к `/api/reserve` всё ещё проксируется Vite на `http://localhost:3000/reserve`.

Для production-сборки выполните `pnpm build`; собранный бэкенд запускается командой `pnpm --filter @app/backend start` (порт задаётся переменной `PORT`, по умолчанию `3000`). Готовый способ собрать и запустить приложение — `mise run docker:build` и `mise run docker:run`.
