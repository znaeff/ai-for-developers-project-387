# Критерии независимого ревью

Этот документ задаёт правила для авторевью и человеческого ревью pull request.
Авторевью читает `REVIEW.md` из **базовой ветки**, поэтому PR не может ослабить
критерии, по которым его проверяют. Ревьюер не правит код и не продолжает
реализацию: его результат — отчёт о проверке.

Источники проверки: diff относительно базы, исходное обращение, связанные
тикеты, спецификация и результаты CI для точного head-SHA. Если ссылка
недоступна или изменение выходит за согласованный объём, ревьюер прямо пишет об
этом и не выдумывает замечания вместо недоступного доказательства.

Отсутствие отчёта, упавший запуск или устаревший SHA не означают «замечаний
нет».

## Шкала риска R0–R3

Риск определяется последствиями ошибки, а не размером diff.

| Уровень | Последствие ошибки | Минимальная глубина проверки |
| --- | --- | --- |
| R0 | Поведение продукта не меняется: документация, процесс, комментарии. | Diff и доказательства автора; полный gate не дублируется. |
| R1 | Локальное обратимое изменение без бронирований, данных и безопасности. | Diff и целевая проверка затронутой границы. |
| R2 | Видимое пользователю поведение или общая бизнес-логика; данные исправимы. | Проверка затронутого поведения и его границ. |
| R3 | Бронирование, доступность слотов, конфликты, потеря данных, приватность или безопасность. | Полная проверка инвариантов, граничных и конкурентных сценариев, разбор отката. |

Для R3 недостаточно зелёного CI: ревьюер проверяет, что тест действительно
воспроизводит опасное поведение. Для R0 достаточно diff и доказательств автора;
повторять полный gate на неизменившемся дереве не нужно.

## Критерии домена

Каждый критерий проверяется по месту в коде, условию ошибки, последствию и
способу проверки. Ссылки на файлы могут смещаться; ревьюер сверяет смысл в
текущем коде, а не только номер строки.

### Слоты и расписание

- Расписание: Пн–Пт, `09:00–18:00` по `Europe/Moscow`, без выходных.
- Кандидаты на начало Слота идут каждые 15 минут.
- Встреча длительностью `durationMinutes` должна целиком помещаться до `18:00`:
  `start + durationMinutes <= 18:00`.
- Показываются только будущие Слоты в окне до 14 дней.
- Длительность Типа встречи — только `15`, `30`, `45` или `60` минут.
- Занятость считается по полуинтервалам `[startsAt, endsAt)`. Два интервала
  пересекаются, если `left.startsAt < right.endsAt && right.startsAt < left.endsAt`.
- У Владельца один календарь: Брони всех Типов встреч занимают общие Слоты.
  Бронь Типа A делает недоступными пересекающиеся Слоты Типа B.
- Занятый Слот остаётся в выдаче с `isAvailable: false`, но не должен
  приниматься в `POST /bookings`.

### API и данные

- Источник истины API — `contracts/main.tsp`; `contracts/openapi/**` и
  `apps/frontend/src/api/generated/**` генерируются и не редактируются вручную.
- `POST /bookings` принимает только существующий свободный Слот выбранного Типа.
  Конфликт возвращает `409`, невалидные данные — `400`, неизвестный Тип — `404`.
- Тело ошибки имеет вид `{ "error": "Текст ошибки на русском" }`.
- Лимит JSON-тела — 1 МиБ; превышение и битый JSON возвращают `400`, а не `500`.
- Время Слотов и Броней передаётся с московским смещением `+03:00`;
  `createdAt` — UTC `Z`.
- Типы встреч и Брони хранятся в памяти процесса и сбрасываются при рестарте.
  Изменение не должно молча обещать сохранность данных.

### Фронтенд

- `/guest`: список Типов встреч, свободные Слоты по дням, выбор Слота, форма
  имени и почты, подтверждение Брони.
- `/owner`: создание Типов встреч и список Броней; обновление по кнопке и при
  возврате фокуса на вкладку.
- Конфликт `409` должен сбрасывать выбранный Слот, перезагружать список Слотов
  и показывать понятное сообщение.
- Занятый Слот остаётся видимым, но недоступным для выбора.
- Навигация выполняется по `window.location.pathname`, без роутера.

### Тесты и проверки

- Полный локальный gate — `mise run check`; он включает workflow lint,
  проверку generated-файлов, lint, typecheck, unit-тесты, e2e, Docker build и
  smoke.
- Результаты проверок относятся только к тому SHA, на котором они получены.
- Если проверка не запускалась, ревьюер указывает это явно и не выдаёт
  отсутствие результата за успех.

### Браузерные доказательства

Для PR с браузерным изменением нужен отдельный артефакт `head-browser-<sha>`,
собранный job `head-browser-evidence` на точном `head.sha` PR.

Согласованные сценарии:

- **Основной** (`@head-browser-main`): Гость выбирает свободный Слот,
  отправляет форму и видит подтверждение Брони; выбранный Слот становится
  недоступным.
- **Соседний** (`@head-browser-adjacent`): после Бронирования Владелец
  открывает `/owner` и видит новую Бронь с типом встречи, именем Гостя и
  временем.

Артефакт должен содержать:

- `head-sha.txt` с SHA, совпадающим с текущим head SHA PR;
- `results.json` — результат Playwright;
- `summary.txt` — SHA, список сценариев и статистика результата;
- `traces/` — Playwright trace для проверки выполнения.

После нового push старый артефакт относится к старому SHA и не считается
доказательством для нового head. Если SHA в артефакте не совпадает с текущим
head PR, проверка не подтверждена.

## Формат замечания

Каждое замечание оформляется одинаково в общем и inline-комментарии:

| Поле | Значение |
| --- | --- |
| ID | `REV-1`, `REV-2`, … уникален в пределах PR |
| severity | `blocker`, `major` или `minor` |
| Блокирующее | `да` или `нет`; `blocker` всегда блокирует merge |
| Критерий | Раздел `REVIEW.md`, спецификация или тикет |
| file:line | Точный путь и строка изменённого файла |
| Условие ошибки | Входные данные, состояние или гонка, которые приводят к дефекту |
| Последствие | Что произойдёт с гостем, владельцем, календарём или данными |
| Как проверить | Команда или тест, воспроизводящий проблему, и ожидаемый результат |

Замечание без `file:line`, критерия и условия ошибки не считается замечанием.
Повторное ревью помечает для каждого прошлого ID статус `исправлено`,
`обосновано` или `открыто` и указывает проверенный SHA.

## Результат авторевью

- Публикуется только `COMMENT`; `APPROVE` и `REQUEST_CHANGES` запрещены.
- Общий комментарий указывает проверенный SHA как `reviewed@<sha>`, риск,
  недоступные ссылки, выход за объём и вердикт.
- Inline-замечание привязывается к изменённой строке diff. Если анкор
  невозможен, замечание остаётся в общем комментарии.
- `reviewed@<sha>` — доказательство проверки, а не одобрение merge.
- Решение о merge принимает человек после проверки head-SHA, CI, замечаний,
  риска и отката.
